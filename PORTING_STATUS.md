# ArgentumForge Porting Status

## Scope

Target: Minecraft Forge 1.8.9 (Forge `1.8.9-11.15.1.2318-1.8.9`), MCP `stable_22`, Java 8, LWJGL 2. This is an experimental port, not a complete Argentum or Celeritas renderer. Everything uses Forge events and reflection: terrain integration replaces `RenderGlobal`'s chunk factory and render container at runtime. The jar contains no Mixin, coremod, tweaker, access transformer or `IClassTransformer`, so it never competes with the Mixin runtime or mixins of clients such as Dawn. The earlier Mixin build is kept on the local `mixin-variant` branch.

**Validation status:** `./gradlew clean build --stacktrace --no-daemon` passes (15 unit tests pass; reobfuscated jar with a plain manifest). The Dawn compatibility changes in this revision were **not run in Minecraft**: nothing below is tested with Dawn or FeatherOpt. The smoke-test record in `TECHNICAL_NOTES.md` belongs to the earlier Mixin build.

## FeatherOpt compatibility review (static only)

The `mixins.featheropt.json` and `mixins.featheropt.cond.json` configurations were inspected. `FeatherOptMixinPlugin.shouldApplyMixin` returns true and `getMixins` adds only the conditional list.

- None of the registered mixins target `RenderChunk`, `ChunkRenderContainer`, `VboRenderList`, `RenderList`, `IRenderChunkFactory`, `RegionRenderCache` or `TileEntityRendererDispatcher`. `MixinRenderGlobal_*` classes exist in the source tree but are not listed in either config.
- `inline.MixinChunkCache_AvoidCopying` redirects `EnumFacing.values()` inside `ChunkCache.getLightForExt`. Snapshot-backed caches override `getCombinedLight`, so that redirect is simply not reached for those builds. Over-budget sections still use vanilla `ChunkCache` with FeatherOpt's redirect.
- `inline.MixinBlockModelRenderer_AvoidCopying` and the Forge model-pipeline mixins still apply, because meshing still uses those classes.
- ArgentumForge does not disable itself when FeatherOpt is present. `disableExperimentalRendererWithFeatherOpt` (default false) turns off only the terrain path, and `disableOptionalEffectsWithFeatherOpt` only the overlay framebuffer effect.
- This review does not prove runtime compatibility.

## Removed with Mixin

Particle frustum culling (`EffectRendererMixin`) and the `FontRenderer.getStringWidth` cache (`FontRendererMixin`) were removed together with the embedded Mixin, the Mixin tweaker and the coremod, because of the risk of a collision with Dawn Client:

- Dawn does not bundle Mixin and requires Mixin 0.8.2 or newer, while this mod shaded Mixin 0.7.11 and started it through its own `TweakClass`. Two Mixin versions on one LaunchWrapper classpath can break either side.
- Dawn has its own mixins on `FontRenderer` and `EntityFX`, the same classes the two removed mixins patched.

Particle throttling through the game's particle setting stays. The Mixin build is preserved on the local `mixin-variant` branch. The `enableParticleCulling` and `enableFontWidthCache` keys are removed from existing config files on load.

## Dawn Client compatibility

The Dawn facts below come from a bytecode analysis of the Dawn and FeatherOpt jars that was provided for this work. No Dawn or FeatherOpt code was copied or decompiled here, and none of it was run.

- Dawn mixins on renderer classes: cached arrays instead of `values()` in `RenderChunk`, `VisGraph`, `ChunkRenderWorker` and `ListedRenderChunk`; a bounds guard in `RegionRenderCache.getBlockState` (default state outside the array); an optional `Thread.sleep` in `ChunkRenderDispatcher.getNextChunkUpdate`; a HEAD hook in `BlockRendererDispatcher.renderBlock`; accessors on `RenderGlobal.viewFrustum` and `renderInfos` for its HUD; hooks in `RenderManager.doRenderEntity`/`renderEntitySimple` and in `EntityRenderer` (rain, fog, camera).
- FeatherOpt: cached arrays in `BlockModelRenderer`, `ChunkCache.getLightForExt` and `FaceBakery`, and overwritten methods in `VertexLighterFlat`/`SmoothAo`.

Review of ArgentumForge against these points:

| Point | Finding | Change in this revision |
| --- | --- | --- |
| a) Weather | **Risk.** With a provider weather renderer (`IRenderHandler`), Forge's `EntityRenderer.renderRainSnow` calls it and returns before the vanilla body, so Dawn hooks inside that body (its weather options) never run. A Dawn hook at the HEAD of the method would still run first. | With Dawn detected, `WeatherRendererController` does not install the renderer and removes it if installed, unless `enableWeatherHooksWithDawn=true`. |
| b) Entity and block-entity wrappers vs. Dawn's `RenderManager` hooks | **OK.** Wrapping happens only when the map value is the exact vanilla class (`getClass() ==`), so renderers that Dawn or other mods replaced are skipped. The entity wrapper changes only `shouldRender`; `doRender` and `doRenderShadowAndFire` go to the original, so hooks in `doRenderEntity`/`renderEntitySimple` still see a normal render call. `setRenderOutlines` is only called on living-entity renderers, which are never wrapped. Restore only puts back entries that are still our wrapper (for block entities every map entry, which covers subclass entries cached by `getSpecialRendererByClass`). If another mod wraps our wrapper, it stays in place but becomes a pass-through once the option is off. Remaining risk: a Dawn hook that casts `getEntityRenderObject(...)` to a concrete vanilla renderer class for arrows, XP orbs or thrown items would fail on the wrapper (not observed; cannot be checked without running). | None. |
| c) Snapshot-backed `RegionRenderCache` | **Risk (hidden errors).** Inside the 20x20x20 region every read is answered by the snapshot. Reads outside it fall back to vanilla, whose unchecked index would throw or read a wrong block; Dawn's guard returns the default state silently instead. | New `debugSnapshotBounds` option (default false): snapshot indices are checked against the region, and every read outside it is counted on F3 and logged (first 10, with stack trace). The F3 counter "out-of-region reads" now counts only reads outside the region; normal in-region fallbacks (empty sections, light at the edge) are no longer counted. |
| d) Snapshot budget with Dawn's worker sleep | **OK.** Nothing waits for workers: the per-frame budget resets every frame, and the `terrainMaxPendingSnapshots` cap (default 256, about 50 KB each) limits waiting snapshots; beyond it sections use vanilla's cache ("capacity" fallbacks on F3). A newer task, a position change or GL deletion discards an older snapshot, so a late compile never uses stale data. Cost of slow workers: memory up to the cap, and a pending cache keeps its chunks referenced until it is consumed. | None. Lower `terrainMaxPendingSnapshots` if memory matters while Dawn's sleep option is on. |
| e) View direction for culling | **Risk (weather only), fixed.** The weather renderer took its forward and side vectors from `view.getLook(partialTicks)` (entity rotation). Freelook (such as Dawn's) or the third-person front view rotate the camera without the entity, which culled columns that are on screen and turned the rain quads edge-on. Terrain bounds culling and the overlay culler read the GL projection and modelview matrices, the same source as vanilla's frustum, so they follow any camera mod that changes the matrices. | The weather renderer now reads its forward and side vectors from `GL_MODELVIEW_MATRIX` and turns directional filtering off above about 60 degrees of pitch, where columns in every direction are on screen. |

Other notes:

- Dawn's array caches in `RenderChunk`/`ListedRenderChunk` apply to the superclass code that our subclasses call through `super`. Expected to be compatible; unverified.
- Dawn's HUD reads `viewFrustum`/`renderInfos`. With integrated terrain those hold our `RenderChunk` subclasses, and `loadRenderers()` replaces `viewFrustum` when the path installs, restores or follows a VBO switch. If Dawn keeps an old reference, its HUD numbers could be stale until it re-reads the field.
- If Dawn's `renderBlock` HEAD hook reads `RegionRenderCache` internals directly (for example through an accessor), it sees the arrays filled on the client thread at construction, not the snapshot.
- FeatherOpt's `ChunkCache.getLightForExt` change is not reached for snapshot-backed builds (`getCombinedLight` is overridden); its `BlockModelRenderer`, `FaceBakery` and `VertexLighterFlat`/`SmoothAo` changes still apply, because meshing uses those classes.

## PR #18 review (closed, not merged)

Each proposal was checked against `main` and Forge 1.8.9; none was reused.

- **Async legacy meshing (`ChunkSnapshot` + executor in `ChunkMeshManager`): rejected.** The worker still calls `BlockFaceMesher.buildChunkMesh(world, ...)`, so it reads the live `World`, `Minecraft` block models and `TerrainLighting` world lookups off-thread. The executor's queue is unbounded and there is no world/revision check before publishing. Fixing it would mean a second background chunk system duplicating the integrated compiler, so the legacy overlay stays synchronous and comparison-only.
- **11-float `GlVbo` layout with lightmap UVs: rejected.** The meshers did not emit consistent lightmap values for every vertex. `draw()` never set a texture-coordinate pointer on `OpenGlHelper.lightmapTexUnit`, so the coordinates were never consumed. Integrated mode already gets real lightmap coordinates from vanilla `DefaultVertexFormats.BLOCK`.
- **`FontAndGlintOptimization`: rejected.** Nothing calls it. It sets blend/depth state, and a static flag can leave `GL_EQUAL` depth and additive blending active. It contains no font, HUD or glint caching.
- **Tile-entity loop and entity bounding-box check in `OptionalRenderHooks`: rejected.** Both compute values and then `continue` or do nothing; they have no effect. Block-entity culling already exists through the renderer wrapper.
